# Maya transport contract and verification

**Reviewed:** November 15, 2026. **Status:** locally implemented contract; no real merchant or sandbox integration verified.

## Source and endpoint decisions

The adapter implements the selected one-time Maya Checkout product. It does not collect card data or use the separate Payments Processing Platform purchase APIs. Configuration is server-only, validates public/secret key classes and environment binding, and accepts no configurable API base URL. Requests use `pg-sandbox.paymaya.com` for sandbox and `pg.maya.ph` for production, as documented in the [current environment guide](https://developers.maya.ph/reference/api-environments) and [host allowlist](https://developers.maya.ph/docs/domains-and-ip-addresses). Requests use HTTPS Basic authentication with an empty password, manual redirect handling, bounded response size and a bounded response deadline. No provider body, credential, buyer profile or payment URL is written to logs.

The following contracts were checked against current official material and the official Maya WooCommerce plugin, pinned to commit `bbeb310a8cd7452cac36673f008decd4316a5ba7`:

## Money and uncertain outcomes

Outgoing JSON emits validated decimal number tokens directly from bigint minor-unit strings, without converting money through JavaScript floating point. Incoming decimal strings remain exact. Numeric responses that cannot safely represent their cents, malformed amounts or unsupported precision fail verification. Normalization supports the documented nested payment amount/status representation and the flat reference-lookup representation. It retains only operational identifiers, amount/currency, raw status, method and relevant capability/time fields; contradictory payment-specific status fields fail verification; it does not persist provider buyer/card details.

A creation request is one POST. The result distinguishes a validated checkout response, a local/provider authentication refusal and an unknown outcome. Timeouts, transport failures, redirects, malformed success, 202/other ambiguous statuses and server failures remain unknown. Payment/refund/void calls never retry automatically. Each unknown result preserves its original non-secret reference or operation/payment identity for reconciliation. GET failures are generic verified-read errors, rather than negative proof. Returned error bodies are not exposed.

The general Payments Processing Platform [retransmission guide](https://developers.maya.ph/reference/know-before-you-code-1) documents optional idempotency with limited matching/retention. That page does not prove the same semantics for this Checkout endpoint and merchant. The adapter sends no assumed idempotency header. A merchant reference does not collapse multiple actual collections. A locally stable operation ID appears in the controlled void/refund reason to aid reconciliation; it is not a provider idempotency guarantee.

Only the environment-specific sandbox `payments-web-sandbox.paymaya.com` or production `payments.maya.ph` / `payments.paymaya.com` HTTPS checkout host is accepted, with a supported checkout path and matching payment ID. An unfamiliar host/path stays unknown for operator review; it is not followed. Real returned-host/path verification belongs to Task 27. Return URLs point only to the configured application payment page and carry opaque booking identity plus display outcome. A return outcome does not confirm money or grant private access; Task 16 must enforce the browser/account status boundary.

## Void and refund capability gates

The adapter requires an explicit capability approval reference, bound environment, maximum amount and enabled operations/methods. None were selected for the real merchant in Task 15. It re-retrieves the actual payment before money dispatch, verifies reference/currency/status, method, payment time and provider `canVoid`/`canRefund` flags. Void is full-only and same Philippine property day. Refund requires the subsequent day and at most 180 days, explicit partial-refund support when needed, and an adequate remaining amount. These supported constraints follow the [current Checkout void/refund guide](https://developers.maya.ph/reference/managing-voids-and-refunds-in-maya-checkout); they do not establish that the Acornelia merchant has those capabilities.

Before a refund, retrieve existing refund operations and conservatively count successful/pending/unrecognized outcomes against remaining capacity. Unknown/malformed balances refuse dispatch. Task 23 must additionally serialize local refund reservations and reconcile externally initiated changes; a read then a POST cannot lock an independently operated merchant account. A malformed or lost money response stays unknown. A verified response retains its own operation ID and parent payment identity. Provider refund completion is distinct from the bank or wallet credit reaching the customer.

The [one-time Checkout guide](https://developers.maya.ph/reference/accept-one-time-payment-using-maya-checkout) documents a default one-hour session. A local hold deadline is not proof the gateway has expired. Task 19 must verify a nonpayable outcome before releasing room/offer capacity. No shorter gateway expiry setting was invented from the synthetic 15-minute hold fixture.

The [current webhook security guide](https://developers.maya.ph/reference/webhook-security) describes RSA-SHA256 signature verification, nonce, millisecond timestamp and two rotating public keys. Task 17 must implement that actual contract; an assumed HMAC secret is not a substitute. No webhook authentication has been verified by this transport test.

## Local evidence and remaining work

Task 18 update, November 16, 2026: platform signature verification and merchant ownership are separate. Maya publishes signing keys per environment; we do not infer merchant ownership from that signature alone. Notifications remain durable wake-up evidence. Before applying money, the worker retrieves payments through the configured merchant's secret-key API. The [RRN endpoint](https://developers.maya.ph/reference/getpaymentviarequestreferencenumber-1) returns an array; every returned actual payment is retained. Missing references can be recovered through a payment-ID read. Actual account scoping and credentials still require the Task 27 merchant checks.

Webhook and merchant-read receipts retain separate immutable provenance. Their delivery timestamps do not create another collection: actual transactions are unique by environment and provider payment ID. Only merchant-read receipts can enter canonical payment application. A delayed/empty read or a success notification followed only by unpaid merchant evidence retries within the work budget; it does not confirm or finish the notification prematurely. Provider calls remain outside retryable transactions, and live completion ownership fences evidence/application/audit effects.

Only an actual `PAYMENT_SUCCESS` collection can fund this one-time booking flow. Authentication and authorization/capture parent states do not fulfill a stay. This deliberately distinguishes the states in the [Checkout status guide](https://developers.maya.ph/reference/understanding-payment-statuses-in-maya-checkout). Actual collection history remains monotonic when older failures arrive. External reversal evidence opens an issue and prevents an older success from funding a previously unconfirmed stay; historical collected money is retained for refund reconciliation.

Canonical application verifies the accepted original reference, environment, exact money, purpose, revision, owner/contact/stay snapshot and physical allocation. One applied-revision marker and one confirmation intent prevent duplicate fulfillment. Additional actual collections, changed money/context, unknown statuses and unavailable paid stays remain visible issues. A released room and offer can be reacquired only under the original approved late policy, with current capacity and a new offer allocation; old released rows never reactivate. No current Acornelia late-payment policy or real collection was approved or verified by these local tests.

Task 17 implements the [documented Webhook Signature V1](https://developers.maya.ph/reference/webhook-security), rechecked November 15, 2026. Verification parses bounded JSON, flattens nested object/array paths, omits empty values, sorts the resulting pairs and appends the nonce before RSA-SHA256 verification. The signature is hexadecimal. JSON whitespace is not signed as raw bytes. Duplicate JSON keys, colliding flattened paths and delimiter-ambiguous values are refused; authenticated retrieval must recover unsupported deliveries. Both distinct RSA public keys must be installed for rotation, with their environment explicitly pinned. Comparing decoded key material prevents one key presented twice from satisfying that requirement.

The delivery timestamp uses milliseconds. The implementation defaults to the guide's five-minute example, rejects past/future timestamps outside the configured bound and never uses delivery time as event identity. Maya's published signing input does not include that header timestamp; timestamp checking alone is therefore not replay prevention. Permanent semantic receipts deduplicate normalized payment identity/status/money/reference/time facts across deliveries. Delivery hashes remain distinct from those receipts. Retention/recovery must preserve this deduplication boundary.

Valid deliveries commit minimal evidence, one typed processing intent and the required audit before acknowledgement. Complete card/profile payloads and signature headers are not stored. Unknown references and statuses remain evidence for the canonical processor; ingestion does not confirm bookings. The local tests prove cryptographic tamper/key checks, fresh-retry deduplication, concurrent receipt creation, restart after lost acknowledgement, SQL immutability and audit-failure rollback. Actual merchant signatures, public-key rotation, trusted ingress/IP configuration and production delivery remain Task 27 checks. Task 18 supplies processing, and Task 26 must admit authenticated evidence while outbound transitions are quarantined.

Contract tests use synthetic records and injected responses, including a real loopback HTTP exchange through native fetch. They cover exact cents and large numeric serialization, multiple collections, one-request unknown outcomes, wrong configuration/key class, private return paths, hostile checkout URLs, bounded waits, provider authentication refusal, lookup failure, full-only void, refund amount fields, merchant/method/time/capacity gates and uncertain money responses. Synthetic fixtures are refused in preview/production; development requires the explicit fixture setting. These are local contract checks, not recorded Maya payments.

Task 16 adds an environment-configured gateway factory and registers checkout creation only when protected keys, environment, capability/method approval and worker timing are valid. It connects committed attempts with lease/ownership fences, private recovery/status and a one-time no-referrer handoff. Missing settings refuse fresh paid preparation outside isolated tests. Tasks 17–19 must establish authenticated evidence, canonical transitions and reconciliation; Task 23 owns local refund reservation/idempotency. Task 26 must fence every outbound call during restore, and Task 27 must validate the actual credentials, merchant, enabled methods, checkout host/expiry and void/refund operation outcomes. Existing secrets were neither printed nor replaced.


## Reconciliation and original checkout identity — November 16, 2026

The [current Checkout flow](https://developers.maya.ph/reference/accept-one-time-payment-using-maya-checkout) identifies `checkoutId` as the payment ID and documents secret-key retrieval by that ID or merchant reference. Task 19 uses those existing GET contracts; it does not invent a retrieve-checkout endpoint. A known original terminal-unpaid result must be consistent with every reference result before expiry. Successful partial reads are processed independently; a missing read never erases money or establishes noncreation.

The guide's default one-hour checkout window is not a local inventory deadline. The implementation requires an approved window and evidence reference, verifies dispatch still has enough original time, and retains a payable/unknown hold past its local deadline. Synthetic tests explicitly use a mocked shorter window. No live shortening/cancellation capability or actual merchant window has been established. Bounded original-link resumption reuses the same verified ID/URL and never creates a new checkout. See the [recovery operating requirements](../operations/deployment.md#payment-recovery-and-safe-hold-expiry--november-16-2026).

## Refund retrieval and POST receipts — November 19, 2026

Task 23 adds a merchant read of `GET /payments/v1/payments/{paymentId}/refunds` with the secret key. The path follows Maya's official WooCommerce plugin client and the [void/refund guide](https://developers.maya.ph/reference/managing-voids-and-refunds-in-maya-checkout). The adapter accepts at most 499 records. Each record needs a UUID refund ID, the same parent payment, an upper-case status, an exact decimal amount and a three-letter currency. A duplicate refund ID, a foreign parent payment, a zero or malformed amount, a non-200 status or an unreadable response makes the whole read unavailable. It is never treated as an empty list. Unfamiliar statuses such as `UNDER_REVIEW` are kept verbatim. Only `SUCCESS` counts as a completed return; for a void, the parent payment's `VOIDED` status counts.

A completed read proves only which refunds were listed. It never proves that an unknown POST did not happen. The synchronous POST response, when verified, is kept as a separate `merchant-post` receipt because the refund list carries no local operation ID. The plugin's linked full Checkout API reference returned HTTP 403 during review, so no further response fields or correlation guarantees were assumed. Contract tests use synthetic responses only. The real merchant's refund-list shape and permissions remain a Task 27 sandbox check.
