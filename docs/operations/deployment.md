## Scheduled work and payment recovery

The local implementation uses an application-owned durable outbox in `work-items`, rather than Payload automatic job execution. Producers enqueue only typed record references in the same transaction as their booking, auth-delivery or enquiry changes. Semantic keys deduplicate matching intent; changing its payload requires a different operation. This selects the queue implementation, not an external scheduler or its subscription.

`POST /api/internal/work` requires the server-only `WORK_RUNNER_SECRET` Bearer credential, regardless of browser cookies. Missing configuration fails closed. Requests select an optional registered kind and a bounded job count; they cannot submit handlers, payloads or database callbacks. Responses expose aggregate counts and omit lease credentials. The endpoint awaits its work before responding. No transport is registered at Task 13: authenticated calls return 503 without claiming records. Maya, reconciliation and mail handlers must pass their owning tasks before registration. No schedule has been installed or verified.

The approved immutable `work` policy must define `leaseSeconds` (5–300), `maxAttempts` (1–20), `maxBatch` (1–100), `backoffSeconds` (1–20 positive entries, each at most 86,400), and `runSeconds` (1–240). These are implementation bounds, not selected operating values. Tests use a 30-second lease, two attempts, five jobs, one/five-second backoff and a ten-second batch budget. Decision 10 must approve actual values, cadence, failure/uncertainty alert thresholds and a named operator before release. The API's 300-second runtime declaration does not verify a hosting plan's function limit; align the policy and verified deployment limit in Task 27.

Claims use serializable transactions, a monotonically increasing generation and an opaque random owner credential stored only as a digest. Completion checks the live owner, generation and unexpired deadline before executing any database-only result callback. Callback effects, work state and required completion log commit together. Network requests occur outside retryable database transactions. Transports must independently recheck the canonical operation's ownership and accepted context immediately before dispatch, accept cancellation, and return database changes as fenced callbacks. Generic queue fencing alone does not establish payment/refund authority.

Expired work that never began dispatch can be reclaimed. Read-only payment/refund reconciliation and guarded hold expiry may also be reclaimed. An expired dispatch of checkout creation, refund or mail becomes `uncertain`; lease expiry and network timeout cannot prove that the provider did nothing. The runner aborts its local wait within the batch/lease budget and persists uncertainty, but cancellation cannot retract an already received provider request. Later results cannot bypass the completion fence. Money handlers must preserve the canonical unknown operation and enqueue outcome reconciliation in Tasks 15/19/23; mail delivery deduplication and provider evidence belong to Task 20.

Safe retries use the configured backoff, repeating its last entry when necessary. Exhausted work becomes failed; uncertain work is retained separately. Protected developer queries show at most 100 failed/uncertain records and indicate additional results. Authorized replay resets attempts and advances the generation, with an atomic action log. Completed work cannot replay, and generic replay of an uncertain checkout/refund/mail dispatch is refused. Reconcile the original operation instead of issuing a second money request or duplicate message. Task 24 supplies the operational UI and alerts.

Migration `20261115_203440_durable_work` preserves existing ready intents with nullable legacy fingerprints. Managed rows receive a validated fingerprint on claim. Malformed legacy payloads are retained as failed work for operator review. Invalid preexisting lease state stops migration rather than erasing history. SQL guards protect intent identity, monotonic generations and completed/uncertain transitions; destructive rollback is refused after managed work exists. Restore-wide external fencing remains Task 26; current environment-mode checks are not proof of cross-process restoration safety.

Persist unfinished payment checks, room holds, and email work in the database. Use short, resumable operations that tolerate repeated execution and a process restart. The runner, schedule, maximum attempts, escalation timing, and responsible operator remain to be chosen.

The selected implementation must reconcile uncertain Maya outcomes, safely expire holds under the booking plan, retry email delivery, and surface unresolved cases to staff. A function continuing after an HTTP response or an in-memory timer is not sufficient evidence of durable recovery.

Authenticate scheduled endpoints and protect manual retry controls. Observe failures and avoid repeatedly processing completed tasks. Test duplicate runs, overlapping runs, lost responses, interrupted execution, and late payment notifications against the existing acceptance checks.

Define durable task claiming, bounded leases and stale-worker rejection before implementation. A reclaimed task must not allow an older worker to overwrite a newer result. Money-moving work with an uncertain external result must be reconciled before another external request; lease expiry is not proof that the provider did nothing. If Payload Jobs is selected on Vercel, configure the required external scheduling/running mechanism rather than relying on a persistent in-process worker. See [Payload Jobs](https://payloadcms.com/docs/jobs-queue/overview). Runner choice, cadence, claim timeouts and escalation remain unresolved launch requirements.

## Recovery and maintenance

Before launch, assign operational ownership, an alert recipient, maximum acceptable data loss, maximum recovery time, data/log retention, and a backup schedule. Supabase's included plan backups must be checked against those needs; do not assume a plan name guarantees sufficient recovery coverage.

Back up database records and uploaded objects under their respective recovery requirements. Test restoration without overwriting live bookings. A code rollback must account for database migrations and external payments; never erase a valid booking or payment simply to match an older deployment.

Supabase database backups contain Storage metadata, not the stored object contents; independently cover uploaded photos and other objects under the selected storage provider's recovery plan. See [Supabase backups](https://supabase.com/docs/guides/platform/backups). A successful database restore is not a complete media restore.

If restoring an older database snapshot, reconcile Maya payments/refunds, recent bookings and room allocations against the recovery point before reopening checkout. Temporarily restrict affected booking operations where their state is uncertain. Preserve later verified financial events and record the reconciliation; do not assume the restored database is current merely because the app starts.

**Recovery quarantine:** Start a restored environment with authentication/private-booking access, booking/offer writes, staff money actions, scheduled workers and outbound payment/refund/email work fenced off before application startup can use them. Checkout closure alone is insufficient: restored pending tasks may already have completed externally, and restored credentials/private links may have been revoked since the backup. Preserve and authenticate incoming provider notifications in a safe durable intake or approved replay process while business transitions are paused. Reconcile external payments/refunds, valid post-backup bookings, room allocations and voucher usage before rebuilding/releasing safe tasks. A named operator must authorize resumption; stale workers must remain unable to commit.

Reconcile restored customer/staff credential versions, roles, deactivations, recovery contacts and booking claims as well as financial state. Invalidate restored sessions and outstanding recovery/claim/booking-view tokens through the tested recovery procedure; revoked links or old password hashes must not become accepted again merely because the backup contains them. If current security evidence cannot be reconstructed, keep affected authentication/private-link access blocked and use an approved recovery process with independently verified authority rather than trusting a restored password or contact address. Preserve valid paid stays even if customer account access needs recovery. The recovery rehearsal must demonstrate how post-backup stay details and redemption state are reconstructed under the approved maximum data-loss target; a provider payment amount alone does not reconstruct room/date/contact details. If required evidence is unavailable, keep affected operations restricted and escalate for an owner-approved resolution rather than reopening uncertain inventory.

During an outage, preserve payment and booking references, reconcile provider state, and resolve uncertain outcomes before asking a guest to pay again. Follow the booking plan for unavailable rooms, overpayments, cancellations, and refund handling. Record the incident, recovery evidence, and follow-up changes in the relevant project documentation.

Assign a named technical operator and backup contact to review provider usage, email delivery, reconciliation failures, application errors, security updates and backup status. The owner pays provider bills directly; that alone does not perform these tasks. The optional ₱3,000/month plan covers original-scope bugs only and does not automatically include proactive monitoring, recurring backup checks, general upgrades or 24-hour incident response. Agree any additional operational service separately, while preserving applicable incident/confidentiality duties. Update this guide whenever configuration, operational responsibility, recovery behavior, or verified deployment details change.

## Refunds, voids and offline reimbursements — November 19, 2026

**Capacity.** A refund is authorized against one actual collected payment and the booking's current revision. Remaining capacity is the lower of the payment's and the booking's verified collections minus completed returns and every authorized, dispatching or uncertain reservation, each counted once. Authorization, its single `refund` work item and its audit entry commit together. A repeated command key returns the original operation; a changed amount under the same key is refused. Void is full-amount and same Philippine day only; refund needs the next day and at most 180 days; partial refunds need explicit approval.

**Dispatch and receipts.** The worker commits `dispatching` and schedules a `reconcile-refund` check before its one POST. Payment/refund/void requests never retry automatically. The synchronous merchant response is stored immediately as an immutable `merchant-post` evidence row, even when the worker's lease has expired. It is the only proof binding a provider refund ID to the local operation. A known refusal releases only that operation's reservation. A timeout or malformed response leaves it reserved as `uncertain`.

**Reconciliation.** `reconcile-refund` work reads the parent payment and its refund list with the merchant secret key and stores each result as evidence. Empty, failed or partial reads never release a reservation. Equal amounts or the operation ID in the refund reason never correlate automatically. After `maxChecks` checks without a final outcome, the operation stays reserved and one `refund-outcome-uncertain` payment issue opens for staff.

**Operator procedure for an uncertain refund.** Do not send another refund for the same money while an operation is uncertain; its amount stays reserved. This marks the request `satisfied` and resolves its open issue. A wrong match is a human error that later reviewed correction must fix; the system does not guess.
